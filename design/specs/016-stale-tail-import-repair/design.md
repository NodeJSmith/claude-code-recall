# Design: Repair stale-tail / ingestion-gap sessions via `ccrecall import --repair-gaps`

**Date:** 2026-09-16
**Status:** draft
**Mode:** sketch

## Problem

`ccrecall import`'s fast-path skip check (`import_session`) trusts a stat match (`file_size`/`file_mtime` equal to the stored `import_log` row) as proof the DB already holds every message from that transcript. When a session's DB rows fall behind its JSONL for any other reason, that stat match is a false positive: `ccrecall import` silently no-ops forever, even though `ccrecall status --check-ingestion` already knows the exact `stale_tail` / `ingestion_gap` sessions and turn counts. Users are told (via `dfl check`'s "Run: ccrecall import" advice) to run a command that cannot fix the problem it's advertised to fix — confirmed live against a real DB (16 sessions, 334 turns unrepaired after running `ccrecall import`).

## Goals

- `ccrecall import` gains a way to actually repair sessions `ccrecall status --check-ingestion` classifies as `stale_tail` or `ingestion_gap`.
- The new repair path reuses the existing per-session classification logic in `ingestion_status.py` rather than re-implementing it, so the two can't drift on what counts as recoverable.
- Repair is opt-in and bounded — it does not change the cost or behavior of a bare `ccrecall import` run.

## Functional Requirements

- **FR#1** `ingestion_status.py` exposes a function that returns, for every session currently classified as `stale_tail` or `ingestion_gap`, its DB session id, project id, and existing on-disk transcript file paths — not just the aggregate counts `summarize_ingestion` already returns.
- **FR#2** `ccrecall import` accepts an opt-in `--repair-gaps` flag. When passed, it force-reimports (bypassing the stat/hash skip check) every session found by FR#1 and reports how many sessions were confirmed repaired (reclassified as `ok` after the attempt) and how many messages were recovered in total.
- **FR#3** Sessions classified as `pending_tail` (modified within the stale-tail grace window — likely still being actively written) or `missing_source` (no surviving JSONL to reimport from) are never touched by `--repair-gaps`.
- **FR#4** The FR#1 lookup and `summarize_ingestion`'s aggregate counts share one underlying per-session classification pass — they must not be two independently-maintained copies of the same stale/gap logic.
- **FR#5** When any repair candidate fails outright during `--repair-gaps`, the command reports a nonzero failure count in its printed summary and exits with a nonzero status, while still completing repair for every other candidate in the batch.
- **FR#6** `--repair-gaps` runs regardless of whether the project-scoped import step it shares an invocation with fails or exits early (e.g. `--project` names a directory that doesn't exist or is judged unsafe) — the two are independent steps, and a bad `--project` value must not silently prevent the DB-wide repair the user asked for.
- **FR#7** `--repair-gaps` does not run concurrently with another `ccrecall import` instance holding the same PID guard (e.g. the SessionStart-spawned background import). If one is already running, the repair step is skipped with a printed notice rather than racing it with a longer-held transaction than normal import uses.
- **FR#8** After force-reimporting a candidate, `--repair-gaps` re-checks that specific session's classification (not a full-DB rescan — just the one session it just processed) to distinguish three outcomes: **repaired** (now classifies as `ok`), **unrepairable** (still classifies as `stale_tail`/`ingestion_gap` even after a full force-reimport — the on-disk transcript itself genuinely lacks the expected messages, so re-attempting it will never help), and **failed** (a file raised during processing — an operational failure, not a data-content one). Each is reported as a distinct count, so the tool can accurately tell the user "this session cannot be fixed" instead of silently re-attempting it every future run or folding it into an ambiguous zero.

## Acceptance Criteria

- **AC#1** Given a DB where a session's `import_log` stat matches its on-disk JSONL but the file's transcript has trailing messages absent from `messages` (a stale tail older than the grace window), running `ccrecall import --repair-gaps --db <db>` inserts the missing message rows, and a subsequent `ccrecall status --check-ingestion --db <db> --json` reports that session no longer counted under `stale_tail_sessions`.
- **AC#2** Running `ccrecall import --repair-gaps --db <db>` against a DB with zero repairable sessions prints a "0 session(s) repaired" summary and exits 0.
- **AC#3** A session classified as `pending_tail` (its transcript's newest mtime within the grace window) is not passed to the force-reimport path by `--repair-gaps` — verified by a test asserting the repair function's candidate list excludes it.
- **AC#4** Against a fixture DB with independently-known `ok`, `pending_tail`, `stale_tail`, and `ingestion_gap` sessions (the test knows which UUID is which by construction), the FR#1 function returns exactly the `stale_tail` + `ingestion_gap` UUIDs and no others, and `summarize_ingestion()` run against the same `sources` snapshot reports `stale_tail_sessions + ingestion_gap_sessions` equal to the FR#1 function's result count. (`summarize_ingestion()` returns only aggregate `dict[str, int]` counts — it carries no per-session UUIDs — so the two are compared by construction-known identity plus count, not by diffing return values against each other.)
- **AC#5** Given a batch of repair candidates where one candidate's file raises during force-reimport (a poison transcript) and the others succeed normally, running `ccrecall import --repair-gaps` still repairs every non-poison candidate, prints a nonzero failed-session count in its summary, and exits with a nonzero status.
- **AC#6** Running `ccrecall import --repair-gaps --project <nonexistent-or-unsafe-dir>` still performs the DB-wide repair (a repairable session outside that project gets fixed) even though the project-scoped import step itself prints an error and does no project import.
- **AC#7** With the `PID_KEY_IMPORT` PID marker already held by a live process, running `ccrecall import --repair-gaps` does not attempt the repair step, prints a skip notice, does not raise, and — critically — does not delete that marker on exit (the other process's guard must survive this invocation's own `finally` cleanup).
- **AC#8** Given a candidate session whose on-disk transcript genuinely lacks the messages needed to close its gap (force-reimport recovers nothing for it and a post-repair reclassification still shows `stale_tail` or `ingestion_gap`), `ccrecall import --repair-gaps` reports it under a distinct "could not be repaired" count in its summary rather than folding it into "repaired" or a silent zero.

## Non-Goals

- `--repair-gaps` does not respect `--project` for scoping — it always scans the whole DB regardless of that flag's value, and (per FR#6/AC#6) regardless of whether the project-scoped import step itself ran, failed, or exited early. Scoping repair to a single project is not needed to close this gap and would add branching for no observed use case.
- No change to `dfl check`'s ccrecall advice text. That lives in the separate `Dotfiles` repo (`packages/dfl/src/dfl/check/ccrecall.py`) — per this session's repo rules, a fix there is filed as a GitHub issue in that repo, not edited from here. File it after this ships, recommending the advice change to `ccrecall import --repair-gaps`.
- No cross-invocation persistence of "known unrepairable" sessions. FR#8 reports which candidates are unrepairable *within a given run*, but the underlying `stale_tail`/`ingestion_gap` classification in the DB doesn't itself distinguish "never attempted" from "attempted and confirmed unrepairable" — so a session FR#8 reports as unrepairable today will still appear as a repair candidate on the next `--repair-gaps` invocation, at the cost of one more force-reimport attempt. That's an acceptable, bounded cost at this tool's personal/manually-invoked scale; a persisted marker (schema change) is out of scope unless `--repair-gaps` moves to automated/repeated invocation.

## Approach

**`ingestion_status.py`** — `summarize_ingestion` already does the exact classification needed (parses each session's transcript, diffs against `messages`, and buckets into `pending_tail` / `stale_tail` / `ingestion_gap` / `missing_source` / `ok`) but only returns aggregate counts. Extract its per-session loop body into a generator, `classify_sessions(cursor, sources, now, stale_tail_seconds) -> Iterator[tuple[str, str, int, list[int]]]` yielding `(session_uuid, category, session_id, missing_indices)` for every session with a verdict (skipping only the cache-hit `ok` fast path, which still short-circuits before classification). It's public (no leading underscore) because, unlike a true module-internal helper, it gets a second cross-module caller below (`import_repair.py`'s post-repair reclassification) in addition to `summarize_ingestion` and `find_repairable_sessions` in this same module. `summarize_ingestion` keeps its existing signature and return shape, now built by aggregating over this generator. Add `find_repairable_sessions(conn, *, stale_tail_seconds=STALE_TAIL_SECONDS, sources=None) -> list[tuple[str, int, int, list[Path]]]` (returning `(session_uuid, session_id, project_id, filepaths)`) that filters the same generator to `stale_tail` and `ingestion_gap` categories, runs a separate `SELECT project_id FROM sessions WHERE id = ?` lookup per match (the classification pass only fetches `sessions.id`, not `project_id`), and pulls `filepaths` from `sources[session_uuid]["existing"]`. Plain tuples cross this boundary, matching this module's existing convention (no new dataclass). Also add `reclassify_session(conn, session_uuid, filepaths, *, stale_tail_seconds=STALE_TAIL_SECONDS) -> str`, a thin wrapper that builds a one-entry `sources` dict for the given session and returns just the category string from `classify_sessions` — used by `import_repair.py` (FR#8) to check a single just-processed session without re-scanning the whole DB. Because the DB's coverage fingerprint changes after a real repair, the `ingestion_check_cache` short-circuit inside `classify_sessions` naturally misses and reclassifies fresh rather than returning a stale cached verdict — no special-casing needed for the post-repair check to see genuinely current state.

**New module `hooks/import_repair.py`** — `import_conversations.py` is already ~430 lines (typical range 200-400 per `coding-style.md`); adding the repair execution loop there would push it further over. A new sibling module mirrors the existing `backfill_runner.py` pattern (shared execution logic factored out of the module that owns the CLI-facing `run()`). Its `repair_sessions(conn, candidates, on_reclaim=...) -> tuple[int, int, int, int]` (returns `(sessions_repaired, messages_recovered, sessions_failed, sessions_unrepairable)`) iterates each `(session_uuid, session_id, project_id, filepaths)` candidate, sorts `filepaths` via `parsing.sort_session_files` (matching `import_project`'s existing multi-file repair-group handling), and routes each candidate through `import_conversations.import_session(conn, filepath, project_id, force=True)` for a single-file candidate, or `import_conversations.import_session_group(conn, filepaths, project_id)` for a multi-file candidate (e.g. a session with a subagent `agent-<uuid>.jsonl` transcript sharing the parent's session UUID) — `force=True` bypasses `import_session`'s stat/hash skip gates, and `import_session_group` parses the union of all the candidate's files' entries in one pass (via `session_ops.sync_session_group`) so `branch_messages` diffing sees every file's entries at once rather than unlinking a sibling file's messages one file-import at a time. `sync_session`'s UUID-dedup insert (`insert_new_messages`) is already idempotent against re-parsing files whose content is otherwise unchanged, so both paths are safe to run repeatedly. After all of a candidate's files are processed (whether or not any raised), if none raised, `ingestion_status.reclassify_session(conn, session_uuid, filepaths)` (FR#8) determines the outcome: category `ok` → increment `sessions_repaired`; category still `stale_tail`/`ingestion_gap` → increment `sessions_unrepairable` (the transcript genuinely lacks the expected content — reattempting won't help). If any file raised, the candidate counts toward `sessions_failed` instead, and reclassification is skipped for it (a poison-file failure is an operational problem, not evidence the source content is missing). `messages_recovered` is measured per candidate as a before/after `SELECT COUNT(*) FROM messages WHERE session_id = ?` delta — taken once before the candidate's file loop starts and once after it finishes (whether or not a file raised) — rather than a sum of `import_session`'s own returned `msg_count`. `import_session`'s second return value is a per-file *total* message count for that session (matching `import_project`'s existing "total per file" convention), not a per-call delta: summing it across a multi-file candidate would overcount, and it would never read 0 on an idempotent re-run of an already-fixed session even though nothing new was inserted. The before/after delta gives the correct "how many messages did this repair actually add" answer in both cases. Wraps each *candidate* (not each file) in one `SAVEPOINT` (`SAVEPOINT import_candidate` / `RELEASE` / `ROLLBACK TO SAVEPOINT`) — a single-file candidate's savepoint spans its one `import_session` call, and a multi-file candidate's spans its one `import_session_group` call, matching the merged-parse change above (a multi-file candidate is now one atomic write unit, not a sequence of independently-committed per-file writes). This visually mirrors `import_project`'s containment block, but **unlike** `import_project`, `repair_sessions()` is never called inside an open transaction (`find_repairable_sessions` is pure-SELECT, and the call site runs after `_run()`'s per-project loop has already committed), so each candidate's `SAVEPOINT`/`RELEASE` cycle commits independently and durably on its own, per SQLite's documented semantics. This is deliberate, not an oversight: a repair run has no cross-candidate invariant to protect (unlike `import_project`'s single-project multi-file case), so per-candidate durability is the *safer* choice here — a run interrupted at candidate 12 of 16 keeps candidates 1-11's repairs rather than losing the whole batch, and is safe to resume by re-running `--repair-gaps` (idempotent per the paragraph above). Both the initial `SAVEPOINT` acquisition and the success-path `RELEASE` are wrapped in the same try/except as the force-reimport call itself: an `OperationalError` at any of these three points is treated as this one candidate's failure (increment `sessions_failed`, log, continue to the next candidate) rather than aborting the whole remaining batch — the code and its comments should describe this as per-candidate durability with per-candidate failure containment, not as "aborting the whole run."

**Wiring in `import_conversations.py` / `cli/commands.py`** — `_run()` gains a `repair_gaps: bool` parameter; when true, after the existing per-project import loop (still inside the same `get_connection()` block, so it reuses the same connection object — see the per-file durability note above for what that connection-sharing does and does not guarantee), it first calls `config.try_acquire_pid_file(PID_KEY)` — the same PID marker (`PID_KEY_IMPORT`) the SessionStart background auto-import already guards itself with via `_spawn_background`'s own O_CREAT|O_EXCL check — and skips the repair step with a printed notice if that marker is already held by a live process (FR#7/AC#7); `--repair-gaps` deliberately extends transaction duration well beyond a normal stat-skip import, so racing a concurrent import raises both the odds and the cost of a `busy_timeout` expiry mid-batch. When acquisition succeeds, it calls `ingestion_status.find_repairable_sessions(conn)` then `import_repair.repair_sessions(conn, candidates, on_reclaim=_reclaim)` and prints `Repaired {n} session(s), recovered {m} message(s)`, plus `, {u} could not be repaired (source transcript is missing the required message(s))` appended whenever `sessions_unrepairable > 0`, plus `, {f} failed — see ccrecall-import.log` appended whenever `sessions_failed > 0`; `run()` exits with a nonzero status only when `sessions_failed > 0` (an operational failure) — `sessions_unrepairable > 0` is not itself a failure exit condition, since it's an accurate, expected report about the data, not something the invocation did wrong. No additional `conn.commit()` call is needed here, since each candidate's files already committed independently inside `repair_sessions()`.

**The PID guard's skip path needs care with `run()`'s existing cleanup.** `run()` already has an unconditional `finally: remove_pid_file(PID_KEY)` that runs for every invocation, on the (previously always-true) assumption that the invocation either owns the marker or the removal is harmless. That assumption breaks the moment `--repair-gaps` can *skip* an acquisition attempt it just made: if `try_acquire_pid_file` returns `False` because another process (e.g. the background auto-import) genuinely holds the marker, this invocation never acquired it — but the existing `finally` would still delete it, silently un-guarding the process that's actually running and defeating FR#7's whole purpose. `_run()` must therefore return whether its repair-gaps attempt was denied the lock (alongside `repair_failures`), and `run()`'s `finally` must skip `remove_pid_file(PID_KEY)` in exactly that one case — every other case (`repair_gaps=False`, or `repair_gaps=True` with a successful acquisition) keeps the exact existing unconditional-removal behavior unchanged.

`cmd_import` in `cli/commands.py` gains a `--repair-gaps` boolean flag (`_FLAG` pattern already used elsewhere in that file) threaded through to `import_mod.run(..., repair_gaps=repair_gaps)`.

## Smoke Test

Using a scratch/dev DB (`--db /tmp/ccrecall-repair-smoke.db`):
1. Import a real project directory normally so a session's `import_log` row records a stat match.
2. Directly `DELETE` the session's last inserted `messages` row (simulating a gap the stat-based skip can no longer see) and rewind the file's mtime past the 15-minute grace window if needed for `stale_tail` classification.
3. Run `ccrecall status --check-ingestion --db /tmp/ccrecall-repair-smoke.db --json` — confirm the session is counted under `stale_tail_sessions` (or `ingestion_gap_sessions`).
4. Run `ccrecall import --repair-gaps --db /tmp/ccrecall-repair-smoke.db` — confirm the printed summary reports 1 session repaired, and the deleted message row reappears in `messages`.
5. Re-run `ccrecall status --check-ingestion --db /tmp/ccrecall-repair-smoke.db --json` — confirm the session count returns to `ok_sessions`.
