# Context: Repair stale-tail / ingestion-gap sessions via `ccrecall import --repair-gaps`

## Problem & Motivation

`ccrecall import`'s stat-based fast-path skip (in `import_session`) treats a matching `file_size`/`file_mtime` against the stored `import_log` row as proof the DB already holds every message from that transcript. When it doesn't — a session classified by `ingestion_status.summarize_ingestion` as `stale_tail` or `ingestion_gap` — `ccrecall import` silently no-ops on that file forever. Users are advised (by an external tool) to run exactly that command to fix the gap, and it does nothing. `ccrecall status --check-ingestion` already knows precisely which sessions and turns are missing; there's currently no way to act on that diagnosis.

## Key Decisions

1. Extract `ingestion_status.summarize_ingestion`'s per-session classification loop into a **public** generator, `classify_sessions` (no leading underscore — it gets a genuine cross-module caller, `hooks/import_repair.py`, in addition to its two callers within `ingestion_status.py` itself), so the existing aggregate-count behavior is unchanged. Add `find_repairable_sessions()` on top of the same generator, filtered to `stale_tail` + `ingestion_gap` categories, returning `(session_uuid, session_id, project_id, filepaths)` tuples (plain tuples across this module boundary — no new dataclass). Also add `reclassify_session()`, a thin single-session wrapper around `classify_sessions` used to check one just-processed session's outcome after a repair attempt (see decision 5).
2. Put the repair execution loop in a new module, `src/ccrecall/hooks/import_repair.py`, rather than growing `import_conversations.py` (already ~430 lines). It calls back into `import_conversations.import_session(conn, filepath, project_id, force=True)` per candidate file, matching the existing `import_project` repair-group pattern (sort via `parsing.sort_session_files`, per-file `SAVEPOINT` containment).
3. `force=True` on `import_session`/`sync_session` bypasses the stat/hash skip gates and re-parses the transcript; `sync_session`'s UUID-dedup insert (`insert_new_messages`) is already idempotent, so re-running repair on an already-fixed session is a safe no-op.
4. Wire a new `--repair-gaps` boolean flag on `ccrecall import` (`cli/commands.py` → `import_conversations.run()`/`_run()`). It runs after the normal per-project import loop (decoupled from that loop's own success/failure — see constraint on `--project`, below), inside the same DB connection, and prints a one-line summary. Each candidate file's `SAVEPOINT`/`RELEASE` commits independently and durably (no outer `BEGIN` wraps the repair batch) — this is deliberate per-file durability, not an all-or-nothing transaction; do not add a `BEGIN` guard to make it "more atomic."
5. After processing a candidate (and only if none of its files raised), re-check that one session's classification via `reclassify_session()`. Three distinct outcomes are reported separately in the summary: **repaired** (now `ok`), **unrepairable** (still `stale_tail`/`ingestion_gap` — the on-disk transcript genuinely lacks the expected content, so retrying will never help), and **failed** (a file raised — an operational problem, distinct from a data-content one). `repair_sessions()` returns all four counts as a `(sessions_repaired, messages_recovered, sessions_failed, sessions_unrepairable)` tuple.
6. `--repair-gaps` guards itself with `config.try_acquire_pid_file(PID_KEY_IMPORT)` (the same marker the SessionStart background auto-import guards itself with) before attempting repair, skipping with a printed notice if another instance already holds it. **This guard's failure path must not let `run()`'s existing unconditional `finally: remove_pid_file(PID_KEY)` delete the other process's still-live marker** — track whether *this* invocation actually acquired the marker (only true when `repair_gaps=True` and acquisition succeeded) and skip the `finally`'s removal when it didn't. Every other invocation shape (no `--repair-gaps`, or `--repair-gaps` that successfully acquired) keeps the exact existing unconditional-removal behavior — this fix is scoped narrowly to the one new case this feature introduces.

## Constraints

- Do not change `summarize_ingestion`'s existing signature or return shape (`dict[str, int]`) — it's used elsewhere (`status.py`) and its aggregate behavior must not change.
- `--repair-gaps` always scans the whole DB and does not respect `--project` for scoping, **and it must still run even when the project-scoped import step fails or exits early** (e.g. a nonexistent or unsafe `--project` value) — the two are independent steps. Restructuring `_run()`'s `if project:` branch from early `return`s to an `elif` chain is required to make this true; this also means the "Total: ..."/"Database size" summary lines that used to be skipped by those early returns will now print even when the project-scoped step found nothing — a deliberate, accepted side effect, not a bug. Do not add project-scoping branches to the repair step itself; that's a separate, explicit non-goal.
- Never touch sessions classified `pending_tail` (still within the grace window — likely actively being written) or `missing_source` (no surviving JSONL) — only `stale_tail` and `ingestion_gap` are repairable.
- Do not edit anything in the `Dotfiles` repo (the `dfl check` advice text lives there) — that's a separate protected repo; out of scope for this change entirely.
- Follow existing per-file poison-transcript containment (`SAVEPOINT`/`ROLLBACK TO SAVEPOINT`) — one bad file must not abort the whole repair batch, matching `import_project`'s existing handling.
- No cross-invocation persistence of "known unrepairable" sessions — `sessions_unrepairable` is a per-run report, not a durable marker. A session reported unrepairable today will still be re-attempted on the next `--repair-gaps` run; that's an accepted, bounded cost at this tool's scale (see design.md's Non-Goals).
