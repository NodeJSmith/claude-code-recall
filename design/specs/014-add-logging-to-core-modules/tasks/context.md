# Context: Add Logging to Silent Core Modules

## Problem & Motivation

25+ of 34 core library modules and several hook-side modules in `ccrecall` (issue #145) have zero logging — several swallow exceptions (`sqlite3.Error`, `json.JSONDecodeError`, `FileNotFoundError`, `OSError`) with no trace, which is a "dark operation" per `rules/common/logging.md`: a failure invisible until a downstream symptom forces someone to reverse-engineer the cause. PRs #149/#150 already fixed 4 core modules + 1 hook module using the project convention. This work finishes the remaining 22 core modules and 3 hook modules with a real fix (plus 3 hook modules confirmed to need none) — the issue's own audit undercounted both figures; see design.md's "Scope correction" subsections for why.

## Key Decisions

1. **Convention** (unchanged from #149/#150): `import logging`, `from ccrecall.models import LOGGER_NAME`, `log = logging.getLogger(LOGGER_NAME)` at module level. Never `basicConfig`, never a handler, never `setLevel` — that's `config.py`'s job only.
2. **Per-module judgment, not blanket application.** Read each file before editing. Apply the CLAUDE.md `logging.md` decision tree per call site (I/O boundary? does the except re-raise? would an operator want to see this in normal operation?) rather than mechanically inserting a log line into every function.
3. **Loop-heavy parsers log a summary, not per-item.** `parsing.py`'s line-by-line JSONL readers must not log once per skipped malformed line — log a count after the loop, per `rules/common/logging.md`'s "log the summary after, not each step during."
4. **`contextlib.suppress()` blocks are the established idiom for intentional, non-fatal swallowing** (`rules/common/invariants.md`) — do not add a log call inside a `contextlib.suppress()` block just because the module is in scope. Verify the failure is genuinely expected and gracefully handled by the caller before treating it as "no logging needed."
5. **Modules with no qualifying boundary are left unchanged.** If a file has no I/O, no swallowed exception, and no meaningful state transition, do not add a decorative `getLogger()` with no log call. Record in your task's evidence that you reviewed the file and found no qualifying boundary — don't skip silently.
6. **`hooks/backfill_query.py` and `hooks/tool_content_eligibility.py` are pure SQL-fragment builders** — string concatenation only, no `except`, no I/O. Expected outcome: no functional change, confirmed by direct read.
7. **`hooks/clear_handoff.py`'s outer `except Exception` already logs** via `log_hook_exception("clear-handoff")` — do not add a second top-level handler. Only its inner `except ValidationError: return` is silent.
8. **Two hook conventions coexist, and both count as "already logs" — don't force a redundant `getLogger(LOGGER_NAME)` module-level logger into a file that already gets one from `config.setup_logging()` or `config.log_hook_exception()`.** Library-style modules declare `log = logging.getLogger(LOGGER_NAME)` at module level. Hook entry points instead call `config.setup_logging(settings, process_name=...)` inside `main()` (returns a configured logger, assign it to a local variable and use/pass that) or `config.log_hook_exception(context)` for a fire-and-forget top-level guard. `hooks/memory_sync.py`, `hooks/warm_model.py`, `hooks/backfill_embeddings.py`, `hooks/backfill_summaries.py`, `hooks/backfill_tool_content.py`, `hooks/backfill_status.py` already use one of these and are **out of scope** — do not touch them.
9. **`hooks/memory_context.py` and `hooks/memory_setup.py` are in scope despite already having some logging** — a `grep -rL getLogger` sweep alone can't tell "fully covered" from "logs something, but still has a silent except block elsewhere," which is exactly what's true of both files (this is why the issue's original audit missed them — read Key Decision 8 and don't repeat that mistake). `memory_context.py`'s `main()` already assigns `logger = setup_logging(settings, process_name="context")` near the top — reuse that variable for the fix rather than creating a second logger. `memory_setup.py`'s `main()` has no such variable; `_needs_reimport`/`_needs_backfill` need one passed in (see T05's prompt for the specific shape, matching `hooks/backfill_status.py`'s existing `logger: logging.Logger` parameter convention).

## Constraints

- Do not touch `db.py` or `tail_pending.py` — out of scope for this sketch (see design.md Approach section for why: `db.py`'s only except block re-raises so it's exempt from the mandatory-log rule; `tail_pending.py` has no qualifying boundary).
- Do not modify already-logged modules: library-style (`search_vector.py`, `db_base.py`, `db_vec.py`, `embed_ops.py`, `embeddings.py`, `health.py`, `import_log_ops.py`, `models.py`, `search_conversations.py`, `session_ops.py`, `tail_resolve.py`, `hooks/context_alerts.py`, `hooks/context_rendering.py`, `hooks/import_conversations.py`, `hooks/session_selection.py`, `config.py`) and hook-main-style (`hooks/sync_current.py`, `hooks/memory_sync.py`, `hooks/warm_model.py`, `hooks/backfill_embeddings.py`, `hooks/backfill_summaries.py`, `hooks/backfill_tool_content.py`, `hooks/backfill_status.py`).
- No test-suite assertions on log output/log capture (`references/common/testing.md` — "No Log Capture Tests" invariant). Verify behavior via the running system (trigger the failure path, read the per-process log file), not by mocking the logger.
- No new dependencies, no schema changes.
- Don't add error handling around scenarios that can't happen — only add logging to `except` blocks and I/O boundaries that already exist in the code today.
