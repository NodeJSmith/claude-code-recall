# CLAUDE.md

Guidance for Claude Code (and humans) working in this repository.

## What this is

`ccrecall` is conversation history and semantic search for Claude Code, shipped two ways from one repo:

- a **Python package** (`ccrecall` on PyPI) providing the `ccrecall` CLI and the hook console scripts, and
- a **Claude Code plugin** (`.claude-plugin/plugin.json`) providing the `/ccr-*` skills and the hook wiring (`hooks/hooks.json`).

It is an independent community project — not affiliated with Anthropic.

## Names (and one deliberate mismatch)

| Surface | Name |
|---|---|
| PyPI package / CLI binary / plugin | `ccrecall` |
| GitHub repo | `claude-code-recall` |
| Skills | `/ccr-recall`, `/ccr-resume` |
| Hook entry points | `ccrecall-setup`, `ccrecall-sync`, `ccrecall-context`, `ccrecall-clear-handoff`, `ccrecall-warm-model` |
| Runtime data dir | `~/.ccrecall/` |

Under a plugin install, skills are namespaced by the plugin name — invoked as `/ccrecall:ccr-recall` etc. The bare `/ccr-recall` form is what the skill folders are named and what a non-plugin (vendored) install exposes.

The **GitHub repo** is `claude-code-recall` while everything else (package, CLI, plugin, data dir) is `ccrecall` — that one mismatch is deliberate: the repo name is more discoverable/descriptive, and renaming a published repo breaks clone URLs and stars. Do not "fix" it.

## Architecture

The hard dependency is on undocumented Claude Code internals (the `~/.claude/projects/<slug>/*.jsonl` transcript layout and the hook-event protocol). Anthropic changes these at patch cadence, so the design contains the coupling rather than spreading it:

- **One parse boundary.** `models.py` (Pydantic) + `parsing.py` own JSONL decoding; downstream code consumes typed objects, not raw transcript shapes. Keep new transcript knowledge here.
- **One active-chain walk.** `parsing.active_chain` is the only place the active set is computed; `find_all_branches` (indexing) and `ingestion_status._expected_uuids` (the ingestion check) both use it. It walks `parentUuid` from the active leaf, crosses each `compact_boundary` through `logicalParentUuid`, and leaves rewound forks out. When that hop resolves, the synthetic `isCompactSummary` message after the boundary is left off the chain; when it doesn't, the walk ends and the summary stays as the only record of the earlier conversation. Bump `ingestion_status.ACTIVE_CHAIN_VERSION` whenever the walk changes which entries it returns: it is part of every source fingerprint, so bumping it invalidates all cached "ok" verdicts and the background import then repairs whatever the new walk finds missing.
- **Background repair.** `ccrecall-setup` spawns `ccrecall import --repair-gaps`, gated by `_needs_reimport`, so gaps repair with no manual step. `find_repairable_sessions` records each ok verdict it had to parse for (committed in batches, all before the first repair candidate), which keeps a steady-state import to a re-check of unchanged sessions without parsing them. Sessions repair can't fix are retried on every background import, with no negative cache. The run's summary goes to `ccrecall-import.log`. A failed or partial import raises a SessionStart alert (see Run history), but unrepairable sessions don't count as failures, so a large unrepairable count in that log is the signal to revisit them. Import and repair never embed: `sync_branch` clears the embedding watermark whenever links changed, and only a manual `ccrecall backfill embeddings` embeds the recovered history. `_spawn_background` takes the import's job lock itself and hands it to the child, which adopts it rather than acquiring again (see One job lock rule).
- **Import locking.** `import_project` takes the write lock only when it has something to write: `unchanged_since_import` skips a file outside any transaction, and `BEGIN IMMEDIATE` runs just before the first write. A deferred `BEGIN` here would fail without waiting if another process committed between its first read and first write, and a read-only scan must not block sync. Every import takes the import job lock and skips (exit 0) if another holds it. `db_base.is_database_locked` is the one check for contention versus a fault, shared with `health.probe_db` and the tool-content backfill's retry: a lock that outlasts `busy_timeout` costs one project or repair candidate, which the next run retries, while other `OperationalError`s still abort. `_run` prints its totals on every exit, and `import_repair.RepairAborted` carries the counts of an aborted repair batch.
- **`content.py:extract_text_content`** returns a 5-tuple: `(text, has_tool_use, has_thinking, tool_summary, tool_content)`. `tool_content` is generic field-join extraction — for each `tool_use` block it walks the `input` dict's string-valued fields (recursively, so nested lists/dicts like AskUserQuestion's `questions` are covered) and joins them into a `[ToolName: ...]` marker, capped per-field and per-block. No per-tool dispatch table; new tool types are covered automatically. Never raises on malformed input.
- **`config.py` / `db.py` / `db_vec.py` split.** `config.py` owns paths, config/settings loading, the job-lock keys, and logging setup — zero heavy dependencies (no fastembed/onnxruntime/sqlite_vec). It's the module hooks that don't touch the DB (health checks, the clear-handoff writer, the warm-model process) import instead of pulling the full `db.py` stack onto the hook hot path. `db.py` owns connections and schema application; `db_vec.py` owns every function that touches sqlite-vec, chunk vectors, or embedding constants (`vec_available`, `chunk_vec_queryable`, `upsert_chunk_vec`, `write_chunk_embedding`, `fetch_branch_messages`, `_ensure_vec_schema`, `ensure_vec`, `branch_embedding_coverage`, `find_stamped_branches_missing_chunks`) — kept out of `db.py` so `get_connection()` stays importable without pulling numpy/fastembed/onnxruntime onto the hook hot path. `get_connection()` is a `@contextlib.contextmanager` (`with get_connection(settings) as conn:`) that commits on success, rolls back and closes on exception, and always closes — no connection is left open on an error path.
- **`schema.py`** holds `SCHEMA_CORE` as a single baseline (embedding DDL folded in), applied idempotently via `CREATE TABLE IF NOT EXISTS` — there is no migration-DML ladder for the base schema. Schema *deltas* on top of that baseline are tracked via `PRAGMA user_version`, applied in a `BEGIN IMMEDIATE … COMMIT` transaction after `SCHEMA_CORE` executes (so a fresh install always has tables before any delta DML runs); a failed delta rolls back and retries on the next connection. The conversations DB is a public contract now; don't evolve it in a way that silently loses a user's synced history. `messages_fts` (a dead FTS index nothing read) has been dropped — `branches_fts`, the live keyword search index, is untouched. The embedding layout is a **two-table design**: `chunks` (one row per exchange — the user turn plus its following assistant turns — carrying the exchange locator, bounded display text, and embedding bookkeeping) and `chunk_vec` (a sqlite-vec virtual table keyed by chunk rowid, 512-dim float vectors). `branches.embedding_version` is retained as a per-branch *watermark* meaning "every current exchange of this branch has a current-version chunk vector"; per-chunk staleness (`chunks.embedding_version`) is the source of truth for query-time filtering. The hot-path framing is unaffected — embedding runs in a detached `sync-current` process, never on the hook thread. Inference memory is bounded by `embeddings.embed_batch`'s planner (attention budget = `max_token_cap²`, where `max_token_cap` defaults to `MODEL_TOKEN_LIMIT` but is set to `SYNC_PATH_TOKEN_LIMIT` on the sync path — plus `EMBED_BATCH_MAX_TEXTS` per `model.embed()` call). fastembed's default `batch_size=256` pads each batch to its longest text, and 256×8192-token fp32 activations exceed 20 GB — an observed WSL-killing OOM. The dominant term is **quadratic** in sequence length: the ONNX export's ALiBi attention isn't fused, so the full seq² score matrix materializes (measured single-text peaks: ~1 GB at ~2.2k tokens, ~4 GB at ~4.5k, ~8.4 GB at the 8192 cap). The budget caps every inference call at one max-length text's attention area, so packing can never exceed the single-capped-text worst case — that residual ~8.4 GB peak is accepted for now (lowering the 8192 cap would change vectors and force a full re-embed; revisit if it bites outside backfill). `get_model` passes `enable_cpu_mem_arena=False` because onnxruntime's arena would otherwise pin that peak workspace forever (growing RSS across a backfill; `malloc_trim` can't reclaim arena memory) — with the arena off the transient returns to the OS after every call. New call sites must go through `embed_batch`/`embed_text`, never `model.embed` directly. `messages` carries a `tool_content TEXT` column (populated by `extract_text_content`, alongside `content` for prose) — the existing `tool_summary` and `has_tool_use` columns remain unpopulated dead columns (`branches.tool_counts` already serves that purpose).
- **Session-keyed branch identity.** `branches` rows are keyed on `session_id` (`branch_ops.upsert_branch`) — one active row per session, updated in place on every sync, instead of a new row per leaf UUID. `is_active` is retained permanently as a guard against pre-existing inactive rows (historical forks); every read path still filters on `is_active = 1`. Don't drop those filters.
- **`session_ops.py` decomposition.** `session_ops.py` is a slim orchestrator (`sync_session`) that delegates to four modules by concern: `import_log_ops.py` (the `import_log` skip check and upsert), `message_ops.py` (session/message row upsert and insert), `branch_ops.py` (branch row CRUD, `branch_messages` diffing, and `sync_branch` — the per-branch coordinator that ties metadata, links, and summary together), and `embed_ops.py` (`write_branch_summary` and `embed_branch_chunks`, the one embed protocol both sync and backfill use — see invariant 3). `sync_session` no longer embeds: `sync_current.run` commits it, then calls `embed_session_branch`. Boundary types between them are plain Python types (ids, dicts, tuples); no new dataclasses cross these module boundaries. `embed_ops._prepare_exchange_data` computes `content_hash` from raw (pre-cap) text, decoupling content identity from embedding quality tier — this prevents sync/backfill ping-pong when different callers use different token caps. `embed_branch_chunks` accepts a `cap_limit` parameter: the sync path passes `SYNC_PATH_TOKEN_LIMIT` (4096, configurable via `sync_path_token_limit` in settings, clamped by `resolve_sync_cap`) to cap the worst-case onnxruntime memory peak at ~4 GB; the backfill path passes `MODEL_TOKEN_LIMIT` (8192) for full-quality vectors. Each chunk's `cap_tokens` column records the cap used when the text was actually truncated (`None` when the text fit without truncation), enabling backfill to detect and upgrade draft-quality chunks via `_diff_exchanges`. `chunks.was_capped` is a dead column (retained in schema, no longer written or read) — `cap_tokens IS NOT NULL` is the live equivalent. `summarizer.py:build_exchange_pairs` (consumed by `embed_branch_chunks`) now appends each assistant message's `tool_content` to the exchange text alongside its prose — including tool-only turns (empty prose, non-empty `tool_content`), which is what makes them embeddable instead of silently dropped. Consecutive identical tool-marker lines are collapsed into one summary line before embedding, so repetitive markers (e.g. 15 `[Read: ...]` calls) don't dilute the prose signal. The vestigial `[Tool: \w+]` regex that used to run over `content` here has been deleted — it matched nothing real.
- **`cli/`** — cyclopts app. Root `App` + `backfill` sub-`App`; commands live in `cli/commands.py` and self-register on import. A single global `--json` flag is the only output-format surface (carried by a frozen `CLIContext`); commands do not define their own `--json`. `launcher` is the error boundary: a `sqlite3.Error` or `OSError` (other than `BrokenPipeError`) escaping a command is logged with its traceback to that process's log, then `errors.classify_failure` turns it into one `emit_error` envelope line on stderr (schema-ahead, locked, disk full, damaged, or a generic fallback) and the process exits 1. `import_conversations.run` leaves those two classes to this boundary rather than logging them itself.
- **Search decomposition.** `search_conversations.py` holds only the two orchestrators (`search_sessions`, `search_messages`) plus `compute_caveat`. `search_query.py` (FTS branch-id lookup), `search_vector.py` (chunk-KNN + snippet hydration), and `search_hydrate.py` (session dedup + card hydration) are separate modules; `search_cli.py` is the CLI-facing formatting layer. Boundary types are plain (branch IDs, score tuples, result dicts) — nothing custom crosses a module boundary.
- **`hooks/`** — the SessionStart/Stop/SessionEnd hook entry points plus the helpers they spawn (`import_conversations`, `sync_current`, `backfill_embeddings`, `backfill_summaries`, `warm_model`, `backfill_tool_content`).
- **`memory_context.py` decomposition.** `memory_context.py` stays the SessionStart hook entry point (`main()`, stdout envelope, DB connection lifecycle) and delegates to three modules: `context_alerts.py` (`proactive_alert_block` — the combined health-alert block, evaluated before every early-return gate), `session_selection.py` (`select_sessions` — the startup/clear session-selection algorithm and its DB queries), and `context_rendering.py` (`build_context`, `build_origin_block`, `pending_question_block` — markdown block rendering and topic extraction). `main()` also reads `db_base.describe_schema_ahead` before opening its connection and passes the result to `proactive_alert_block`, so a database newer than this install is reported even when that connection fails; the CLI launcher prints the same check to stderr. It passes `db_path` too, so the alert block can read that database's `runs.json`.
- **`backfill_embeddings.py` decomposition.** `backfill_embeddings.py` keeps the `run()` orchestrator plus the per-batch `_reclaim_memory` helper (gc + `malloc_trim` between batches, the same RSS discipline as import). `run()` starts with `clear_false_watermarks`, which clears the watermark on every branch `db_vec.find_stamped_branches_missing_chunks` reports: a stamped branch with an exchange that never got a chunk is invisible to `build_selection`, which only sees chunks that exist. The check is read-only, and `ccrecall doctor` reuses it to report those branches as missing vectors; `backfill --status` still counts them as embedded until a backfill runs. Each branch commits on its own, and batch selection only takes ids above the last one seen, so a run attempts a branch at most once and one it couldn't finish waits for the next run. A lock timeout costs that branch alone, and three in a row abort the run. `backfill_query.py` owns query construction (`build_selection`, `days_modifier`), the shared constants both the orchestrator and the status reporter agree on (`BATCH_SIZE`, exit codes). The CLI command takes the backfill's job lock (`config.JOB_KEY_BACKFILL_EMBEDDINGS`) before `run()`, with its `days` and `limit` as the record's scope (skip-not-queue when another instance holds it, exit 0 for scheduler friendliness) — a second concurrent backfill would double the onnxruntime memory peak. `backfill_status.py` owns read-only progress counting (`count_status`), duration formatting, and the `--status` report (`run_status`). `backfill_runner.py` owns the outer batch-loop driver (`run_batch_loop`: select → limit cutoff → stuck-batch detection → per-item dispatch → batch trailer) shared by `backfill_embeddings.run()` and `backfill_tool_content.run()` — both callers supply their own per-item processing, exception taxonomy, no-progress recovery action, and batch-trailer extras via callbacks; only the outer loop shape and stuck-batch detection are shared, not the domain-specific behavior.
- **Per-process logging.** Each process type writes to its own rotating log file (`~/.ccrecall/ccrecall-<process>.log`, 1MB/2 backups) via `config.py`'s `setup_logging(settings, process_name=...)` — avoids multiple processes racing on one file's rotation. Process names: `setup`, `sync`, `context`, `clear-handoff`, `import`, `backfill-embed`, `backfill-summary`, `backfill-tool-content`, `warm-model`, `cli` (the last one is what a direct, non-spawned `ccrecall <command>` invocation gets unless the command sets up its own process-named logger, as the spawned background commands do).
- **Run history (`run_history.py`).** Import, repair, sync and embedding backfill each record their finish in `<db>.runs.json`, beside the database: per kind, the newest run (`last`) and the newest unscoped success (`last_ok`). `record_run` wraps a run's work after its job lock and early exits (a run that attempted nothing records nothing), records an exception as `failed`, and records nothing on Ctrl-C. A body has no default outcome: every success path calls `finish(OUTCOME_OK)`, and one that returns without calling `finish` records `failed`, so a forgotten path never reads as ok. Each abort path sets its own reason, since return codes can't tell them apart. Recording is best-effort and imports no vector modules. A run that never finished is read from its job lock's record (`job_lock.probe` on the kind's `KIND_JOB_KEYS` key): a held lock means running, a free lock with a record left in it means killed. `failed_run` and `is_busy` are the one definition of a failed run and a busy one, shared by `doctor`'s `<kind>-failed` findings and the SessionStart failed-import alert (`alertable_import_failure`, which skips busy runs, as `doctor` files them under working); `describe_reason` is the shared reason prose. Repair alone writes `<db>.unrepairable.json` (session ids with the source fingerprint they were tested against): a completed repair replaces it, an aborted one only adds.
- **One job lock rule (`job_lock.py`).** Every background job (import, sync, embedding backfill, summaries backfill, model warm) runs only while it holds an exclusive, nonblocking `flock` on its `~/.ccrecall/.lock-<key>` file, and a job that can't get it skips. The holder writes a JSON record into the file (PID, key, start time, scope: an import's `repair_gaps`, a backfill's `days` and `limit`, and the resolved database path `db`; build it with `import_scope`/`backfill_scope`) and empties it on release, which every exit path including Ctrl-C reaches through `with`/`finally`. Liveness comes from the kernel, never from a PID: `probe` takes a shared nonblocking lock, so held means running, free with a record means killed, and empty or missing means nothing ran. The file isn't deleted in normal operation; the one exception is a file this user can't open, which is recreated. `_spawn_background` (`job_lock.spawn`) takes the lock in the parent, writes a record with no PID, and passes the descriptor to the child via `pass_fds` and `CCRECALL_JOB_LOCK_FD`; the child's `acquire` adopts it, so the lock passes with no gap. A handed descriptor open on another key's lock file stays in the environment for that key's `acquire`, so a child that takes another lock first still adopts its own. `doctor` reads scope through `repairs_gaps`/`drains_backlog` to decide whether a running import repairs gaps and whether a running backfill drains the whole backlog; a job whose scope names another database doesn't count. Tests hold a lock from another process with the `hold_job_lock` fixture and leave a killed one with `leave_killed_lock`.
- **Findings (`findings.py`) and their renderers (`status.py`).** `diagnose` collects every finding about an install through one read-only connection, inside one deferred read transaction, and writes nothing, the ok-verdict cache included (`summarize_ingestion` is read-only; only the repair scan warms that cache). A finding's `group` is its severity (`action`, `working`, `none`), and the verdict is the worst group present. Each check is isolated: one that raises becomes a `check-failed` finding. `status.py` renders `status` (verdict plus one line) and `doctor` (the full report, `--list`, exit codes) from the same `Diagnosis`, with one `--json` shape. Finding ids, group names, `summary` keys and exit codes are a public contract. SessionStart alerts keep their own hot-path checks in `health.py`; fix commands both surfaces print live there as `FIX_*` constants.
- **`health.py`** — the parse/format boundary for the **surfacing model** (the SessionStart proactive alerts + the reactive recall caveat). Owns the two small JSON sidecars under `~/.ccrecall/` (`embedding-status.json`, `alert-snooze.json`), the active writability probe, the told-once-snooze ledger, the reason-code → prose mapping, and the alert-block builder. Deliberately imports **no** vec/fastembed/onnxruntime — it only ever *reads* the embedding-status sidecar (see invariant 3). Embedding-failure is detected by the detached embedding process writing that sidecar, never by probing capability on the hook path.

### Four invariants to preserve

1. **Hook stdout.** The hooks print `{"continue": true}` / `{}` to stdout for the harness. Never emit anything else to their stdout.
2. **Hook hot path.** Hooks are separate console scripts, *not* `ccrecall hook …` subcommands, because routing them through the cyclopts app eager-imports the whole command surface (fastembed/numpy/onnxruntime, ~1800ms) vs ~440ms for a direct hook import. The no-lazy-imports rule (see Conventions) means you cannot dodge that, so keep hooks as direct entry points.
3. **Embedding health is read, never probed, on the hook path.** The SessionStart hook learns that embeddings are failing by *reading* `health.py`'s `embedding-status.json` sidecar — it must never load the vector extension or the embedding model to check capability inline, or it would pull the ~1800ms stack onto the ~440ms hot path. The authoritative detector is the detached embedding process (`sync_current` / `backfill_embeddings`), which records/clears that sidecar. `health.py` is structurally guarded to import none of vec/fastembed/onnxruntime (a test asserts this via AST inspection). `embed_ops.py` owns the write-path half of this invariant, and no write lock is held during inference: `embed_branch_chunks` reads and diffs with no write transaction, commits the watermark clear on its own, infers with no transaction open, then runs one `BEGIN IMMEDIATE` write transaction (skipped when nothing was inferred and it would neither stamp nor prune) that re-reads the branch, discards vectors whose exchange text changed, and stamps the watermark only if every exchange's chunk is then current at full quality. The caller must have no transaction open, or it raises `sqlite3.ProgrammingError`. A crash during or after inference leaves the branch selected by backfill; the one unguarded point is between sync's commit and the clear when links didn't change, which the next sync on that session heals. Those transaction boundaries must not change across module splits. While a backfill holds its job lock, sync commits its messages and the clear, then skips inference so the two memory peaks don't stack.
4. **One active branch per session.** Post-migration, `branches` is `UNIQUE(session_id)` — a DB-level constraint that makes a second row for the same `session_id` impossible, enforced by the v1 migration rebuild (`db_base.py`'s `_migrate_to_v1`, re-exported through `db.py`), which runs unconditionally on every `get_connection()` call while `user_version < SCHEMA_VERSION`, including on a brand-new install. `ccrecall doctor` and `status` still run a standing runtime check (`findings.count_branch_invariant_violations`) and report a `duplicate-active-branch` finding if it's ever violated — this is defense-in-depth for the upsert logic, not evidence that the schema allows duplicates. `SCHEMA_VERSION` reached `4` at this point in the ladder: `_migrate_to_v2` purges orphan messages and drops the dead `fork_point_uuid` column via table rebuild (SQLite has no `DROP COLUMN`-in-place path here) — `SCHEMA_CORE` and `_migrate_to_v1` both still carry `fork_point_uuid` deliberately, so a fresh install stays compatible with v1 running first; only the v2 rebuild removes it. `_migrate_to_v3` adds `file_size` and `file_mtime` columns to `import_log` for stat-based fast skip — runs outside the version gate (with duplicate-column error handling for concurrency) because the columns must exist even when `user_version` is ahead of this code's `SCHEMA_VERSION`. `_migrate_to_v4` adds `messages.tool_content TEXT` — additive and unconditional like `_migrate_to_v3`, for the same reason (the column must exist regardless of which `SCHEMA_VERSION` the running code targets). `SCHEMA_VERSION` reached `7` at this point in the ladder: `_migrate_to_v5` adds the `ingestion_check_cache` table, `_migrate_to_v6` adds its `db_coverage_fingerprint` column, and `_migrate_to_v7` added six `summary_enrichment_*` columns to `branches` for the LLM summary feature. **That feature has been deleted** — nothing reads or writes those columns any more, and the dead `summary_source_hash` column from `SCHEMA_CORE` joins them. All seven are retained rather than dropped: dropping them needs a `branches` table rebuild, and a rebuild is exactly the reshaping migration that requires the sqlite-vec extension to be loaded first (see the `chunks_vec_ad` trigger). They come out alongside the next migration that reshapes `branches` for real, once the migration test matrix in #121 exists to cover it. `_migrate_to_v8` adds `chunks.cap_tokens INTEGER` (the effective per-chunk embedding token cap used to distinguish draft-quality sync-path chunks from full-quality backfilled ones) plus the partial index `idx_chunks_cap_tokens ON chunks(cap_tokens) WHERE cap_tokens IS NOT NULL`, unconditional like v3/v4, for the same reason (the column and index must exist regardless of which `SCHEMA_VERSION` the running code targets). `SCHEMA_VERSION` is now `9`: `_migrate_to_v9` rebuilds `projects` without `UNIQUE` on `path` (#221). A project's identity is its normalized `key`; `path` is metadata that moves with the repo, and a unique path turned a moved repo into an `IntegrityError` that aborted every import. Unlike v3–v8 it is a reshaping migration, so it runs inside the version gate after `prepare` loads sqlite-vec, like v1/v2. It builds `projects_new` and renames it into place, copying every `id` verbatim; it never renames `projects` away, because since SQLite 3.26 a rename rewrites the `sessions.project_id` FK to follow the renamed table. `project_ops.upsert_project` owns the write rules that make a non-unique path safe: an accurate path (a cwd) always replaces the stored one, and a lossy slug-decoded path is written only when inserting a new row.

## Conventions

Enforced by `prek` hooks (`prek.toml`), including `house-lint` (configured in `pyproject.toml`):

- **No `from __future__ import annotations`** and **no lazy imports** (imports inside functions) — both have dedicated checks. A defended lazy import carries `# house-lint: ignore-next[HSL002] - <reason>`. Use `X | None`, not `Optional[X]`.
- **`whenever`** for all date/time, not stdlib `datetime` (convert only at library boundaries).
- **setuptools** build backend (never hatchling). License is declared as an SPDX expression (`license = "MIT"` + `license-files`).
- **Conventional Commits.** Releases are automated by **release-please**; the version lives in `pyproject.toml`, is mirrored into `.claude-plugin/plugin.json` (release-please `extra-files`), and `uv.lock` is re-locked on the release PR by a `sync-lockfile` CI job so its self-version never drifts. `feat`/`fix`/`perf`/`refactor`/`docs` land in the changelog.
- **Logging coverage on new files.** New files under `src/ccrecall/` or `src/ccrecall/hooks/` should be checked against `rules/common/logging.md`'s decision tree before merge. A one-shot `grep -rL getLogger` inventory does not re-run itself — three separate audits during the 014 logging effort each missed a file the previous one had (a hook module logging via `setup_logging()` instead of a literal `getLogger` call, and `hooks/backfill_runner.py`, created by a PR that landed between the original audit and the design's execution).

## Gotchas

- Skills under `skills/` are bundled into the plugin; their `references/` subdirs are loaded on demand by the skill, not eagerly.
- **Windows is explicitly not supported** (README: "Supported platforms: Linux (including WSL2) and macOS. Windows is not supported."). Don't design around cross-platform (POSIX + Windows) concerns — e.g. a `fcntl.flock`-based lock is a complete fix, not a partial one requiring a `msvcrt` fallback. `pyproject.toml`'s classifiers list Linux/macOS only. `hooks/subprocess_utils.py`'s `sys.platform == "win32"` branch predates this policy and shouldn't be read as evidence of Windows support.
